# Simulation Scoping & Input Architecture

> How per-turn work stays bounded and how keys reach the game, and why; [`ARCHITECTURE.md`](../../ARCHITECTURE.md) §6 holds the rules and wins any disagreement (flag it, §8.2).

## Bounded Simulation Scoping
Only the active floor is simulated: other visited floors are stored (`engine.storedFloors`), not run. Within it, per-actor work is bounded.
- **Dormant actors:** every living actor on the floor stays in `EnergyScheduler` and accrues energy. On its turn, `Monster.takeTurn()` resolves status ticks (always, asleep or not), checks paralysis and stun, dispatches an awake monster's `onTurnStart` hooks, then calls `MonsterAI.decideAction()`, which resolves a pending wind-up and spell cooldowns first. A sleeper wakes if it has line of sight to the hero within 8 or stands on a tile in the hero's FOV, within the hero's wake radius (`wakesOnSight`, [ADR-0014](../decisions/0014-wake-radius-in-fov-awakening.md)); otherwise it returns a `WaitAction` with no pathfinding, item use or combat. `GameEngine.updateFov()` wakes sleepers on visible tiles the same way; damage and alarms wake one regardless. Companions never sleep and are scheduled like any other actor.
- **Memory:** a hostile monster knows where its target is only while it perceives it (`perceives`, `src/engine/ai/perception.ts`: adjacent, or in line of sight within its sight radius, cut by its own statuses as the hero's is, and never through an opaque gas). Each such turn it stores the tile in `Monster.pursuit` (saved); out of its senses it walks there, searches around it for a while, then stands until it perceives the target again (`src/engine/ai/pursuit.ts`). Waking, a blow (`Monster.takeDamage`) or an alert (`Monster.alert`: an alarm, a call for help, a choice's `alertMonsters`) tells it where the target is.
- **Pursuit cost:** a monster closing on a goal (`stepTowardAction`) runs its own path search only within 10 tiles, giving up after the 21×21 tiles around it, so one walled in by a crowd stays cheap. Beyond that, or when its search fails, it steps along the floor's shared distance field to that goal (`src/engine/ai/distanceField.ts`): one breadth-first pass per goal per turn (up to 8 goals cached per map) serves every monster headed there, so each monster's own cost is a look at its eight neighbours. Fleeing (`ai/flight.ts`), calling for help and pack flanking (`ai/packTactics.ts`) are bounded box scans and searches of the same kind.
- **Scheduler partitioning (evaluated, not adopted):** an active/dormant scheduler partition was implemented, benchmarked and reverted; `EnergyScheduler` keeps one flat list. Read [ADR-0001](../decisions/0001-scheduler-partitioning-evaluated-not-adopted.md) before trying again.
- **Bounded FOV:** `FovManager` computes visibility by recursive shadowcasting limited to the hero's radius (default 8, adjusted by pacts and `Player.sightBonus`). Awakenings and bestiary records are checked only across the bounding box of the hero's vision. Each update demotes only the tiles the previous pass lit, tracked as packed indices, so the cost follows the view, not the map; `revealAll` sets a flag that makes the next update fall back to one full sweep, cheaper than tracking every index. On a lit map (`GameMap.lit`, the town when `town.lit` is set) shadowcasting reaches the whole map, but the awakening and bestiary box stays the hero's radius. `lit` is not saved: `TownMapGenerator` sets it, and a load re-derives it (`restoreFloorLight`, `src/engine/storage/serializer.ts`).
- **Perception-radius override:** any active status whose handler declares `StatusHandler.perceptionRadius` forces `updateFov()`'s radius to that value (the smallest wins), a generic mechanism rather than a per-status check: `blindness` and `sensory_masked` declare 1, and a pack may declare its own (cotw's dark floors). The same statuses limit a monster's sight (`ai/perception.ts`). A radius under 2 is a senses limit and is kept; the hero's own radius is never under 2.
- **Sensory Masking & Echolocation:** the `sensory_masked` status cuts FOV to 1 through the override above, and separately lets the renderer show what the hero hears: `getAudibleEntitiesInRadius`/`getAudibleTilesInRadius` (`src/engine/fov/echolocation.ts`, radius 6) find non-dormant actors (a sleeper makes no noise) and noisy terrain in a bounded query, and `CanvasRenderer.renderEcholocationView()` draws only those over a blank board. The FOV and awakening simulation is unchanged; only what is drawn changes.
- **Spatial bucketing:** entity lookups use coordinate bucket maps (`entityBuckets: Map<string, Entity[]>` keyed `"x,y"` in `GameMap`), so proximity and collision checks don't scale with the monster count.
- **Modal pause:** pushing the first modal onto `ModalStackManager` sets `engine.isPaused`, and `advanceWorldUntilPlayerTurn()` does nothing while paused. The pause stops idle advancement only: an action a menu issues through the command bus (a potion drunk, armour swapped) lifts it for that action, so monsters answer it as they would with the menu closed.

## Input Architecture
`InputHandler` (`src/rendering/input-handler.ts`) owns the `window` `keydown`/`keyup`/`blur` listeners, the `ModalStackManager` and the `ChordBuffer`; no other key listener sits on `window`. A key held with Ctrl, Alt or Meta is left to the browser (Ctrl+F finds, Ctrl+R reloads), except `Ctrl`/`Cmd+K`, the command palette, and Alt with a movement key, which does nothing: Alt+Left is the browser's Back, which would leave the game.
- **`ChordBuffer` (`src/ui/input/chordBuffer.ts`):** with arrow chording on (the default), orthogonal arrows pressed within a micro-debounce window (`arrowChordBufferMs`, default 40 ms, clamped to 25–75) combine into a diagonal. Releasing the arrow that started a pending step flushes it at once, since no chord can follow it: waiting out the window after the key is up is latency felt on every step. Browser key repeats skip the window; the opposite arrow cancels the pending step and takes its direction; `blur` clears all held-key state. Only arrows are buffered; numpad, vi keys and WASD dispatch at once.
- **Bindings:** defaults live in `src/ui/settings/settingsManager.ts`. The player's are saved (`yodc_settings`) as changes only, so a default changed later reaches every action the player left alone. Every default key maps to exactly one action (`defaultKeybinds.test.ts`), including the keys `InputHandler` answers before reading any binding (`HARD_WIRED_KEYS`), which Settings refuses to bind elsewhere. A Shift key is the chord `Shift+<code>`, read before the bare key; Ctrl, Alt and Cmd chords are refused, since they belong to the browser.
- **The companion wheel (radial menu, `src/rendering/radialMenu.ts`, `src/ui/companionWheel.ts`):** a hold-to-open canvas overlay on the bindable `radial_menu` action (default V). `InputHandler` fills its eight wedges from `companionWheelSlots(engine)`, which names everything from the companion and the pack's `trainerSkills`. The wedges are fixed so the hand learns them: N calls the companion or sends it away, NE/E/SE are its first three learned skills, S opens its pack, and SW/W/NW are kept for orders a companion will take once the engine has a generic companion-order capability. While held, the directional keys pick a wedge instead of moving; releasing the trigger confirms, `Escape` cancels, a blur closes it. Without a companion there is no wheel, only the line "You have no companion to command." It registers on `ModalStackManager` like other overlays. Gamepad invocation is not implemented. **[Deferred: P-24]**

## Focus & Modal Isolation
- **Rule:** every open modal registers on the LIFO `ModalStackManager` (`src/ui/modalStack.ts`). The top modal receives every key; if it doesn't handle `Escape`, the stack pops it; all other keys are trapped so none reaches the simulation. Handlers `preventDefault()` the keys they consume, so browser shortcuts don't fire.
- **Keyboard focus:** keys reach `InputHandler`'s `window` listener whatever has focus, but focus left on a HUD button behind a dialog let Tab walk out onto the HUD (the soak's chaos lens logged it hundreds of times a night). So a modal that returns an element from `focusRoot()` has its focus kept by the stack: opening moves focus into it, Tab and Shift+Tab cycle its shown controls (unless the modal already took Tab), the modal beneath takes focus when one leaves, and when the last leaves focus returns to what had it before. Modals that hold focus on their own overlay leave `focusRoot` out. `modalStackFocus.test.ts` covers the rules and `e2e/gameplay.spec.ts` the real dialogs.
- **Modals outside the game:** the feedback and settings modals also open from the main menu, where `InputHandler` is disabled, so each takes keys through a `keydown` listener on its own focus-holding overlay, never a second `window` listener, and stops their propagation. That listener runs before `InputHandler`'s, which rebinding needs: the key to bind reaches the settings modal before `InputHandler` would claim it.
- **No accidental commits:** a window that opens mid-move (a choice, a mastery-perk choice) only stages a selection until Enter or a confirm button; a level-up never opens a window (a badge pulses and a toast names the key). The shop, which opens inside the step that bumps its keeper, ignores its trade keys as auto-repeats and for 250 ms after opening, so a movement key held into a merchant buys nothing. A level's points are planned in `AttributeAllocationDraft` and reach the player only on Accept (`Player.allocateAttribute`, `allocateRuneMastery`).
- **The character menu:** modals implement `UIModal` (`id`, `isOpen`, `handleKeyDown(e): boolean`, `close()`). `CharacterMenuModal` (`src/ui/characterMenu/`) is one tabbed shell that owns the chrome (tab strip, close button, a footer of the active tab's keys from `MenuTab.footer()`); tabs draw only their content, consumed through the `MenuTab` interface, and decline keys they don't use, which the shell then reads as tab switches from the player's bindings. `src/ui/` imports only types from `src/rendering/`, so a tab that shows sprites takes a `drawItemIcon` callback from `src/main.ts`.
- **Inline overlays:** the map and inspect overlays are intercepted by `InputHandler` right after modal-stack routing: an open map receives every key (`MapOverlay.handleKeyDown`) and absorbs what it doesn't use. For a single non-nesting overlay this equals stack gating (`mapOverlayInput.test.ts`).
- **Screens, not modals:** `InputHandler.enabled` covers whole-screen transitions (entering the game, the main menu, the game-over screen, the title and saga screens). They are not modals over a live simulation, so the stack does not apply; dialogs that open only from them (Load Saved Game, the hall of fame, `showConfirmDialog`) take keys on their own focus-holding overlay, never the browser's `confirm()`.

## Presentation Models
HUD panels that summarize the game compute their content without the DOM, from engine state after each turn, so tests check them headless: the console (`src/ui/console/consoleModel.ts`), the combat sidebar (`src/ui/sidebar/sidebarModel.ts`), first-time hints (`src/ui/hints/hintModel.ts`, shown ones saved as `hint:<id>` in `Player.tutorialFlags`) and the prologue's action cues (`findActionCues`). `ViewportManager.recalculate()` (`src/rendering/viewport.ts`) fits the map canvas to what the real mounted HUD bars leave, re-running on a `ResizeObserver` of each bar.
