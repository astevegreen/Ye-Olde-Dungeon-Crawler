# State Normalization, Storage & Schema Evolution

> Sub-document of [`ARCHITECTURE.md`](../../ARCHITECTURE.md) §5 stub. This file is **explanatory**: mechanism detail and worked examples. Every **binding** rule — the reference invariant, the forward-only migration rule, the version floor, the load-failure invariant — is restated in the core document's §5 stub. If this file and the core document ever disagree, the core document wins; flag the conflict rather than resolving it here (`ARCHITECTURE.md` §8.2).

- **Reference Invariant:** Persistent game state contains no live circular object references. Relationships between entities, containers, and items use scalar IDs (`parentId`, `ownerId`).
- **Current State Representation:**
  - **Entities:** `GameMap` keeps a `Map<string, Entity>` keyed by ID, plus spatial indexes (§6).
  - **Tiles:** a dense `TileDefinition[][]` grid indexed `[y][x]`. Dense arrays are the intended representation for per-cell map data.
  - **Ground items:** `Map<string, Item[]>` keyed by plane-qualified coordinate (`planeId:x,y`).
  - **Items in containers:** containers hold `Item[]`. Each item carries scalar `parentId`/`ownerId` (schema v8), resolved at runtime through the module-level container registry (`src/engine/items/containerRegistry.ts`). Saves serialize containers as nested item trees carrying those IDs.
  - **Flat item index (`src/engine/items/itemIndex.ts`):** containers still hold their items, but lookup by ID goes through a flat `Map<id, { item, location }>` rather than walking packs, belts, purses, paperdolls, and floor tiles. `location` records whether the item sits in a container, on the ground at a coordinate, or in an equipment slot.
    - Entries are written at the choke points every item passes through: `Container.addItem`/`removeItem`, `GameMap.addItemAt`/`removeItemAt`, and `Paperdoll.equip`/`unequip`. `GameMap.removeItemAt` retracts only the ground entry it wrote, so a pickup — which stores the item (registering its container) before clearing the tile — keeps the newer entry. A stack merged into another (coins by denomination) retires its id outright. Deserialization routes through `Container.placeItem`, which registers the index as `addItem` does but skips capacity checks and merging, so a load rebuilds the index with no schema change and puts back exactly what the save held.
    - `EngineCommandBus.resolveItem` resolves IDs through the index; reachability is unchanged (carried, worn, or underfoot).
    - Scoped questions ("is this item in *this* inventory?") stay structural via `InventoryManager.findItemById`.
    - This is a second structure tracking a first, which is how the scheduler partition failed ([ADR-0001](../decisions/0001-scheduler-partitioning-evaluated-not-adopted.md)). `itemIndex.test.ts` audits the index against a full structural scan after a save/load round trip.
  - **Player innate capabilities & rune state:** Innate rune power and dimensional recall anchors persist as scalar fields on `Player` / `SerializedPlayer` (`hasDiscoveredRune`, `runeCharges`, `runeMaxCharges`, `deepestRecallFloor`, `recallPosition`, `runeMastery`, `runeChannelBankedTurns`). The dual-energy model (`Player.energyModel`, unlocked by content — e.g. the CotW blood-magic grimoire) persists as the optional `SerializedPlayer.energyModel` (`SerializedEnergyModel`: structured/volatile energy and maxima, `vitalityTenderBurned`); a save without it loads with no energy model, i.e. never unlocked. Because these are backward-compatible optional fields with graceful defaults, none of them required a schema version bump.
  - **Item definition and stack size:** `SerializedItem.definitionId` and `quantity` (written only above 1) are optional. A save without `definitionId` takes it from the manifest item with the same name (`itemDefinitionLookup`, skipping names two definitions share), so the potion row, relic checks and stacking, which key on it, work after Continue. A save without `quantity` loads each stack as one item: those sizes were never written. No schema bump. Containers reload their children without merging, so stacks the player split stay split.
  - **Junk mark:** `SerializedItem.junk` (written only when set) keeps the hero's junk mark (`Item.junk`: a shop sells all of it at once, auto-pickup leaves it); a save without it loads every item unmarked. No schema bump.
  - **Lasting max HP share:** `SerializedPlayer.maxHpPercentBonus` (written only when set) is a temple blessing's share of max HP (`Player.maxHpPercentBonus`, applied in the attribute calculator's multiplier phase); it is restored before HP is clamped to max HP, and a save without it loads as 0. The save keeps the base max HP, so the share never compounds. Granted blessings are world flags. No schema bump.
  - **Item definition-only fields:** the save holds what a run can change. What only the definition holds — potion `effects`, `twoHanded`, `blocksSlot`, `rangedConfig`, `predicate`, `hooks` — comes back from the manifest item named by `definitionId`, exactly as `createScaledItem` gives it to a new item, the way monsters get their loot tables, affliction, tags, targeting mode and `hooks` back. An item with no definition keeps the old behavior: a potion's effects derived from its `potionType` and potency.
  - **Container opened flag:** `Container.wasOpened` (set by `markOpened()` from the loot/store actions and the zero-cost `open_container` command; the HUD badges ground containers: gold star unopened, amber dot with remaining items, grey check once emptied) persists as the optional `SerializedContainer.opened`. Absent in older saves, which load as never opened — backward-compatible, so no schema bump.
  - **Monster catch-up scale:** `Monster.catchUpScale`, the total multiplier floor catch-up has applied to a survivor (`FloorManager.simulateCatchUp` raises it to a visit's multiplier, never past it, so returns don't compound), persists as the optional `SerializedMonster.catchUpScale`, written only above 1. Absent in older saves, which load as unscaled: no schema bump.
  - **Cleared-floor respawn timer:** `GameMap.lastRespawnTurn` persists as the optional `SerializedMap.lastRespawnTurn`, so a reload on a cleared floor waits out the rest of the interval. An older save without it starts the interval at the load (`floorTurnCount`): no schema bump.
  - **Perks:** `SerializedPlayer.perks` holds the ids of the perks the hero holds (`manifest.perks`), resolved against the pack on load (an id the pack no longer declares is dropped), and `carriedAtStairs` the ids of the items carried when the stairs were last taken (Lore-Keeper); both absent when none, so no schema bump.
  - **Compendium category perks:** chosen category-mastery perks persist as the optional `compendiumCategoryPerks` map (save and profile), keyed by `MonsterCategoryDefinition.id`; category kill totals are derived from the per-species kills, not stored. Absent in older saves — none chosen — so no schema bump. A species record saved as tier 3 with fewer than `SPECIES_MASTERY_KILLS` kills (mastery once took 5) loads as tier 2, unless its optional `studiedTier` (a rank bought from the sage, tracker 4.1; absent in older saves) is higher. A species record's `chosenPerk` is legacy (Q7 "A", tracker 3.5: perks come from families only): `deserializeGame` hands it to `CompendiumManager.convertSpeciesPerks`, which makes it the family's perk when the family has none and drops it otherwise, once; it is no longer written. A family's choice may be a pack family perk's id (`PerkDefinition.category`, tracker 3.6); on load a choice the pack no longer offers that family is forgotten (`forgetUnofferedPerks`), so the mastery asks again.
  - **Worn items:** a save's paperdoll is put back slot by slot as it was worn (`Paperdoll.restore`), not through the equip rules, which run before the hero (and the perks that bend them, Giant's Grip's shield beside a two-hander) exists.
  - **Container capacity and coins:** a container's capacity (`maxWeightCapacity`, `maxBulkCapacity`) comes back from its definition when it has one, like its hooks, since nothing in a run changes it. Coins weigh nothing and take `COIN_BULK_CM3` each, so a purse's capacity is a coin count. An older save's purse may hold more coins than it now has room for: `InventoryManager.settlePurse` moves the excess to the pack, cheapest coins first, after the paperdoll is restored. Platinum was dropped (three metals remain): a saved platinum coin loads as ten gold, and that overflow is settled the same way. No schema bump.
  - **Item quality labels and families:** `ItemQuality` is `normal | artifact`; the old `enchanted`, `cursed` and `broken` labels went with the item families ([ADR-0012](../decisions/0012-item-families-as-pack-data.md)). An older save's label loads as `normal` (`legacyQuality`), and an item saved as `cursed` with no modifiers whose definition pins a family (`ItemDefinition.family`, the four cursed relics) loads with that family's tier for its own floor, so it stays bound. Family modifiers are saved whole on the item (`SerializedItemModifier`), so a template change never alters an item already found. No schema bump.
  - **Merchant stock:** each town merchant's stock persists as the optional `SaveData.merchantStock` (merchant id -> serialized items), so a bought item stays gone and a sold one stays on the shelf. On load an item whose id the manifest's `initialInventory` authored comes back as that manifest item (its availability `predicate` is code-side data, not saved); anything else is deserialized. A save without the field gets the authored stock, so no schema bump.
- **Seeded PRNG Serialization:**
  - `PRNG` (`src/engine/dungeon/prng.ts`, exported alias `Mulberry32`) keeps a single 32-bit internal state. It is saved as `SaveData.prngState` via `getState()` and restored via `setState()` on load, so the random stream resumes exactly where it stopped.
  - Replay determinism holds for simulation code: randomness and spawned-entity IDs both derive from the engine PRNG (§7.2). Save timestamps and profile IDs are deliberately outside that boundary.
- **Persistence Architecture & Storage Tradeoffs:**
  - **`localStorage` Backend:** synchronous default for character saves (`ProfileManager`) and autosaves (`AutosaveManager`, periodic and on floor change). Both live in `src/engine/storage/` and accept a `Storage`-shaped adapter; in the browser, `src/main.ts` supplies `window.localStorage` through `getBrowserStorage()` in `src/ui/platform.ts`. At boot, `src/ui/persistenceInit.ts` requests persistent storage (`navigator.storage.persist()`).
  - **Per-Pack Key Namespacing:** every storage key the engine owns is derived from the active manifest id — `ProfileManager.rosterKey`/`saveKeyPrefix` and `AutosaveManager.autosaveKey` — so two content packs sharing one origin never read or overwrite each other's rosters, saves, or autosaves. There is no un-namespaced fallback key: a bare key left by anything else on the origin is ignored, never adopted. Engine-owned keys carry no pack name of their own (the hall-of-fame ledger is `yodc_hall_of_fame`).
  - **Quota Management:** map tiles and FOV exploration are run-length encoded (`compaction.ts`). Schema v11 introduced dictionary-based tile RLE (`tileCodes: string[]` on `SerializedMap`, with `${count}:${index};` tokens), replacing the fixed 26-letter single-char table and allowing arbitrary content tiles. It is the only tile codec: a serialized map carries its own dictionary, and run-length data arriving without one is recorded by the flight recorder rather than silently decoded into walls. The synchronous payload is bounded to the active floor: `ProfileManager.saveCharacterBounded` writes inactive floors to the async tier first, then writes a save carrying only the active floor plus `archivedFloors` (the offloaded floor numbers). Schema v10 introduced that field.
    - The offload is awaited rather than fired and forgotten: trimming floors out of a synchronous write before their archive write completed would lose them if the archive failed. Only floors that actually landed are trimmed, and a failed offload falls back to the full inline payload.
    - `hydrateArchivedFloors` puts them back at load, which is an async boundary; `GameEngine.changeFloor` is synchronous, so a floor cannot be awaited mid-turn. A floor the archive cannot supply is simply absent and regenerates from its seed on revisit, exactly as a never-visited floor would.
    - FOV exploration stays inline: it is RLE-compressed and small, so a floor's explored map survives even when its tiles do not.
  - **Asynchronous tier (`src/engine/storage/asyncStore.ts`):** `AsyncKeyValueStore` is the contract for bulk records that would otherwise strain the synchronous quota — every visited floor, bestiary records, and flight-recorder logs. The engine defines the interface only: `indexedDB` is a browser global and engine code may not touch those (§2), so `IndexedDbStore` lives in `src/ui/indexedDbStore.ts` and is injected by the composition root. `InMemoryAsyncStore` backs headless callers (tests, `npm run sim`), so engine code depends on the tier without depending on a browser.
  - **`BulkArchive` (`src/engine/storage/bulkArchive.ts`)** is the typed surface over that tier: per-profile floors (`putFloor`/`getFloor`/`listFloors`/`deleteFloors`), bestiary records, and flight-recorder log dumps. Keys are profile-scoped so two characters never collide. `src/main.ts` constructs it with the IndexedDB store when available and archives the flight log on a crash; an archive failure is swallowed so it can never mask the crash it is recording.
  - **Native File Export/Import:** `.cotw` file download via `Blob` (`src/ui/platform.ts`), file and drag-and-drop import (`src/ui/saveImporter.ts`), and Base64 save codes (`src/engine/storage/saveTransfer.ts`) provide zero-dependency offline backup, run sharing, and cross-browser transfer.
- **Forward-Only Schema Migrations (`src/engine/storage/migrator.ts`):**
  - Saves are wrapped in a `VersionedSaveEnvelope` (`schemaVersion`, `contentManifestId`, `timestamp`, `data`). `CURRENT_SCHEMA_VERSION` in `migrator.ts` is the authoritative current version. Do not restate its value in this document or elsewhere; read it from `migrator.ts`.
  - `SchemaMigrator.migrate()` applies registered `N -> N+1` steps in sequence. It throws when the payload is unparseable, newer than the engine, missing a step, or a step fails.
  - Every breaking save-format change increments `CURRENT_SCHEMA_VERSION` and registers exactly one new forward-only step. Existing steps are never rewritten except as a confirmed bug fix (§8.1).
  - **Version floor:** the current version is also the oldest readable one. A save below the floor is refused by `migrate()` (surfacing as `migration-failed`, Load Failure Handling below) rather than silently mis-decoded. The v0 -> v11 step chain and the legacy tile codec it depended on were deleted pre-launch — see [ADR-0002](../decisions/0002-v0-v11-migration-chain-deletion.md) for why and under what authorization. `SchemaMigrator` keeps its registration and sequencing machinery, verified by `npm run validate:schema` and `migrator.test.ts`, so the next real migration behaves exactly as it did before that deletion.
- **Load Failure Handling:**
  - **Invariant:** a failed load never yields a partially-loaded engine and never overwrites the stored payload.
  - **Typed outcomes:** `ProfileManager.loadCharacterResult()` and `AutosaveManager.loadAutosaveResult()` return a `LoadOutcome` (`src/engine/storage/loadResult.ts`): either the loaded game, or a failure naming one of `missing`, `corrupt`, `newer-than-engine`, or `migration-failed`, with a player-facing message and the underlying error as `detail`. `classifyLoadError` maps the messages `SchemaMigrator` throws; anything unrecognised is `corrupt`, since the save exists but could not be read.
  - **Notification:** `src/main.ts` routes every load through helpers that show the failure message as a toast when `shouldNotifyPlayer(failure)` is true — that is, for everything except `missing`. A missing save stays silent, because starting fresh or having no autosave yet is routine.
  - The older `loadCharacter()` / `loadAutosave()` methods remain as thin wrappers returning the game or `null`, so callers that do not care why a load failed are unaffected.
- **Death and Continue:**
  - `ProfileManager.saveCharacter` and `AutosaveManager.autosave` skip the payload write when `engine.player` is dead. The death handler's save still updates the roster (`questStatus`, epitaph, level), so the Hall of Fame and roster record the death, while the slot keeps the last living save.
  - `resolveContinueTarget` (`src/engine/storage/continueTarget.ts`) is the one rule behind the main menu's Continue: the autosave if its hero hasn't fallen, else the most recently saved living hero, else nothing. `MainMenu` uses it for both the button label and the click.
  - A fallen hero's earlier saves remain loadable from Load Saved Game; loading one yields a living run again, because the profile comes back from the save payload, not the roster.
- **Autosave Preservation:**
  - The autosave key is per content pack, not per hero, so one slot serves every character and any later autosave — another hero's, or the same hero's after climbing back up or loading an older save — replaces it.
  - `AutosaveManager.autosave` therefore calls `preserveIfSuperseded` before writing: the current autosave is copied verbatim to `<manifest>_autosave_preserved` when it belongs to a different hero or its floor is deeper than the incoming one. The preserved slot is overwritten unless it holds the same hero's deeper run, so repeated retreats keep the deepest run. A failed preserve write (quota) is recorded and never blocks the autosave.
  - `AutosaveSlot` (`'latest' | 'preserved'`) selects the slot in `getAutosaveMetadata` and `loadAutosaveResult`; `clearAutosave` clears both. `SaveSlotModal` (Load Saved Game) shows an "Earlier Autosave" card for the preserved slot. Continue (`resolveContinueTarget`) and the game-over Load Autosave button use only the latest slot.
  - Cost: a second copy of a full save payload in `localStorage`, present only after a superseding autosave. Only one preserved run is kept per pack.
