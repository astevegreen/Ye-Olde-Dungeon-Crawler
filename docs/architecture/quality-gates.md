# Automated Quality Gates

> Sub-document of [`ARCHITECTURE.md`](../../ARCHITECTURE.md) §7.2 stub. This file is **explanatory**: what each gate script actually checks and how. Every **binding** rule — the requirement to pass all gates, the exact gate command list, the PRNG-discipline invariant, the encapsulation invariant — is restated in the core document's §7.2 stub. If this file and the core document (or the scripts themselves) ever disagree, the scripts and the core document win; flag the conflict rather than resolving it here (`ARCHITECTURE.md` §8.2).

- **Requirement:** every change must pass the gates below before merging. Coding agents run the relevant gates locally and report real output. `npm run gates` runs all of them in order — lint, tests, sim, schema, build, then Playwright (which needs the build) — stopping at the first failure. It always runs lint and the tests, then stamps them so the next commit's pre-commit hook can skip them (below). Agents commit but rarely push, so without it the pre-push gates (Playwright above all) would first run at the owner's push.
- **Current CI:**
  - `.github/workflows/ci.yml` (*Quality Gates*) runs on every pull request to `main` and on manual dispatch: `npm run lint`, `npm test`, `npm run sim`, `npm run validate:schema`, then `npm run build` (cotw only; WarCraft is parked, [ADR-0010](../decisions/0010-warcraft-pack-parked.md)).
  - `.github/workflows/deploy.yml` runs the same gates on push to `main` (and manual dispatch), then deploys `dist/` to GitHub Pages.
  - `.github/workflows/playwright.yml` runs on pushes and pull requests to `main`: it builds the bundle and runs the Playwright smoke suite in `e2e/`.
- **Local pre-commit hook:** `.githooks/pre-commit` runs the fast gates — `npm run lint` and `npm test` — before every commit. The `prepare` npm script points git at it (`git config core.hooksPath .githooks`), so `npm install` wires it up; `SKIP_HOOKS=1` bypasses it deliberately. The slower gates run in the pre-push hook and in CI rather than on every commit.
  - **Gate stamps:** the hook does not rerun a gate that already passed on this exact working tree. Over 553 hooked commits (21 Sep to 7 Oct 2026), 35% reran lint and the unit tests on a tree where both had just passed, mostly the second and later commits cut from one working tree ("one request per commit", §8.4 in `ARCHITECTURE.md`), at about 38 s each. `scripts/gate-stamp.ts` (`lib/gate-stamp.ts`) keeps a stamp per tree under `.git/gate-stamps/<hash>.json`: per clone, never committed, the newest 40 kept. The hash covers the content of every tracked file and every untracked, not-ignored file (so an edit, an added file or a deletion makes the stamp miss) plus the Node version; gitignored files are not in it, `package-lock.json` is. The hook writes a stamp after lint and the tests pass, and `npm run gates` writes one after its own lint and tests.
  - **A stamp is a cache of a pass, never an authority.** Any doubt runs the gate: a tree that cannot be fingerprinted (no git, an unreadable file, a nested repository) runs every gate and writes nothing; a stamp is written only if the tree is byte-identical before and after the gates ran; a gate that fails writes none. `npm run gates` always runs lint and the tests, because it exists to produce real output, and then stamps them. `GATE_STAMP=off` ignores stamps entirely (none read, none written), `SKIP_HOOKS=1` still bypasses the hook, and deleting `.git/gate-stamps/` resets it.
  - **What it does not cover:** a bare `npm run lint` or `npm test` writes no stamp (a filtered `npm test -- <file>` proves nothing about the tree, and wrapping the scripts would change them for CI too), so those runs do not shorten the next commit; `npm run gates` does. The slow gates (sim, schema, build, Playwright) are not stamped, and the pre-push hook still runs them in full. `npm run gate-stamp -- status` says whether the current tree is stamped for lint and test.
- **Local pre-push hook:** `.githooks/pre-push` runs the slower gates — `npm run sim`, `npm run validate:schema`, `npm run build`, and `npx playwright test` — before anything reaches `origin`: one to two minutes, the sim and Playwright taking most of it (about 70 s on a quiet machine, sim 20 s, schema 2, build 7, Playwright 40; a 2026-10-07 run beside other work took 2 minutes, sim 43 s, schema 2, build 9, Playwright 69). Commits go straight to `main`, and `ci.yml` runs only on pull requests while `deploy.yml` runs after a push, so without this hook the slow gates would first run after the code had already landed. `SKIP_HOOKS=1` bypasses it.
- **Local commit-msg hook:** `.githooks/commit-msg` (§8.1, §8.4) rejects a commit that stages a protected file (`actionPipeline.ts`, `engine.ts`, `migrator.ts`) unless the message names its exception as `§8.1 exception N`, and rejects one whose message carries no attribution trailer (`Co-Authored-By: Claude` or `Agent: <name>`; the owner's own commits use `Agent: owner`). It only warns, never blocks, when a large commit spans several areas. `SKIP_HOOKS=1` bypasses it, as with pre-commit.
- `.gitattributes` pins LF endings for every text file, in the repository and in the working tree (`* text=auto eol=lf`), whatever the checkout's `core.autocrlf` says, and `.editorconfig` tells editors the same. Git for Windows defaults `autocrlf=true`, which left a mixed tree where a script matching `"\n"` silently missed CRLF files. `.githooks/**` and `*.sh` are named explicitly as well, because a CRLF `#!/bin/sh` line breaks the hook under `sh`.
- The Playwright suite runs the built `dist/index.html` over `file://`. `npx playwright test` (the pre-push hook, `npm run gates`, `playwright.yml`) runs six of the nine specs in `e2e/`, in Chromium, Firefox, and WebKit unless noted:
  - `smoke.spec.ts` asserts it boots to the main menu with no uncaught errors.
  - `gameplay.spec.ts` plays it — a new hero moves and spends a turn, the pipeline sees the real `MovementAction` class name (minification keeps names), an open map absorbs movement keys and closes on Escape, and Save & Exit then Continue restores the run — then checks the HUD's layout across window sizes, the modal stack and keyboard focus through the dialogs, and aiming and hovering with the mouse.
  - `exhaustive-playtest.spec.ts` takes one hero through the console HUD, coin pickup and hover, the target overlay, the inventory, the campfire grottos, runestones, the floor-50 ending's stakes, altars, and Save & Continue.
  - `feedback-and-diagnostics.spec.ts` opens the feedback window from the main menu, the in-game header button and F3, switches its modes, and opens F2's triage tab, with the keys kept out of the game while each is open.
  - `whole-run.spec.ts` (Chromium only, about 10 s) plays three runs through real keys and clicks, setting scenes with the F2 triage API where walking there would take hundreds of turns: a shop buy, a pact sealed with the pact keeper (and its first-time hint), the stairs, a level-up spent on the Character tab, a spell aimed onto a rat, an altar rite, Save & Exit and Continue, and the slain ending through its portal to the score screen; the driven-off ending through the portal home; and a death, with the fallen hero in the hall. Keys the game can let pass (an effect playing, right after a load) are pressed until their effect shows; `WHOLE_RUN_URL` points it at a dev server.
  - `prologue.spec.ts` (Chromium only) plays a new hero's opening: the controls note holding the keys, the night raid's objective and countdown, a villager running free once her thrall is gone, the drink cue on the potion slot, the hero struck down instead of slain, and the dying gate-ward's choice.
  - **Opt-in**, run by no gate: `playwright.config.ts`'s `testIgnore` leaves these out unless the run names the spec or its tag, or sets its variable. `campaign-flow.spec.ts` (`npm run test:campaign`) talks to a townsperson, fights a spawned goblin, and takes the stairs to the next floor; `gameplay-record.spec.ts` (`npm run test:record`) plays 30 s of moves, menus and casts on video (`RECORD_DURATION_MS` sets the length); `soak.spec.ts` (`SOAK=1`) is one overnight soak run, looped by `npm run soak` (below). The two scripts run Chromium only, and need `npm run build` first like the rest.
  - Every spec but `prologue.spec.ts` that starts a new hero calls `e2e/newHero.ts`'s `pastTheOpening`, which answers the note and ends the raid from the F2 triage API. Locally the suite runs on a quarter of the logical cores (`playwright.config.ts`): at Playwright's default of half, Firefox tests timed out under the load.
- **Overnight soak (no gate runs it):** `npm run soak -- --lens player|chaos --from N --count N --actions N --until HH:MM` (`scripts/soak.mjs`; `--help` lists the rest) runs `e2e/soak.spec.ts` with `SOAK=1` once per seed, in Chromium against the built bundle, until the count or the cutoff: a seeded bot plays a hero through real input and checks the game after every action. Each seed's action log and summary, the lens's `findings.jsonl` with its screenshots and traces, and a `runs.jsonl` line per run go to `.prompts/soak/<lens>/` (gitignored). `--start-floor N` (`SOAK_START_FLOOR`) soaks the floors the bot never reaches on foot: past the opening, `engine.diagnostics.outfitForFloor(N)` levels and dresses the hero as one who reached floor N might be (`--start-level` overrides the level, by default 1 + 0.7 × N), and `jumpToFloor(N)` drops it there. Its runs go to `.prompts/soak/<lens>-floor<N>/`, and each summary records its `startFloor`.

Each static gate below (purity, encapsulation, creep, palette) fails when it inspects no files, so a run from the wrong directory or after a directory moved is never a silent pass.

No test writes into `src/`: several suites walk it in parallel workers (`replayBuilders.test.ts`, `packNeutralSource.test.ts`, `uiPalette.test.ts`, `docReferences.test.ts`, and the gate runs inside the gates' own tests), and a file listed by `readdirSync` and deleted before `readFileSync` fails them with `ENOENT`. A gate's regression test plants its violation in a temp directory instead: `check:engine-purity` and `check:engine-encapsulation` take `--overlay <tree-path>=<file>` (repeatable, `scripts/lib/gate-overlays.ts`), which scans `<file>` as though it sat at `<tree-path>`: it joins the walk of the directory it names (the encapsulation gate compiles it there, so its relative imports resolve into the real engine), and is scoped and reported by that path. Without the flag a gate sees the tree as it is.

1. **Architectural Purity & Boundaries (`npm run check:engine-purity`, `scripts/check-engine-purity.ts`):**
   - Scans every `.ts` file under `src/engine/`, `src/content/`, `src/ui/`, and `src/rendering/`. Content source files are checked for DOM tokens regardless of whether they are registered as hooks, because file location never exempts simulation code (§2).
   - **DOM and browser tokens:** fails on `window.`, `document.`, `navigator.`, `localStorage`, `sessionStorage`, `HTMLElement`, `CanvasRenderingContext2D`, `HTMLCanvasElement`, `ImageData`, `globalThis`, or `OffscreenCanvas` in engine and content source files (test and fixture files are exempt), and on the browser-only forms of names an ordinary identifier may share: `self.`/`self[`, `location.href` and the other `Location` members (a local `location.x` passes), and `new Image`.
   - **Reverse imports:** fails on any `src/ui/` or `src/rendering/` import in `src/engine/` (tests included), and on `src/content/` imports in engine production source.
   - **Content isolation:** fails on `src/ui/` or `src/rendering/` imports in content source, and on any `engine/<path>` deep import in content source (test and fixture files exempt).
   - An import, for every import check in this gate, is any module specifier a file names: `import … from`, `export … from`, a side-effect `import '…'`, a dynamic or type-position `import('…')`, or `require('…')`, across line breaks. A specifier computed at run time (`import(path)`) is invisible to the scan. `scripts/__tests__/purityGatePatterns.test.ts` plants each form at an engine, content, or presentation path (through `--overlay`, above) and asserts the gate reports it at that path and line.
   - **Public API:** fails on any `engine/<path>` deep import in `src/ui/` or `src/rendering/` (tests included) or in `src/main.ts` **and `src/main/**`**, and on content imports in UI/rendering source. `src/main.ts` alone is checked for content-pack imports and permitted to have them, as the sole composition root (§3); files under `src/main/` are presentation scope for import purposes but may **not** import content packs. `scripts/__tests__/mainScopeGateWidening.test.ts` (run by `npm test`) is the regression test proving this: it plants a file at `src/main/` (through `--overlay`, above) with a deep engine import and a content-pack import and asserts `check:engine-purity` fails on both, reporting it at that path. Sibling cases do the same for `check:engine-encapsulation` with a direct `engine.turnCount = 0` mutation and a nested `engine.lastActionResult.pipelineError` write; `encapsulationGateWidening.test.ts` plants its subsystem-call and bracket-write cases at `src/ui/` the same way, and its cast-alias case at `src/content/cotw/`.
   - **Timing and audio globals:** fails on `setTimeout`, `setInterval`, `clearTimeout`, `clearInterval`, `requestAnimationFrame`, `cancelAnimationFrame`, `requestIdleCallback`, `performance.now`, `AudioContext`, `webkitAudioContext`, `HTMLAudioElement`, or `new Audio` in engine and content source files, on the same execution-path rule as DOM tokens (§2).
   - The success line reports how many engine and content **source** files were scanned and how many test/fixture files were exempt, rather than counting exempt files as covered.
   - **Unseeded randomness:** fails on `Math.random` (dotted or `Math['random']`) and `crypto.getRandomValues`/`crypto.randomUUID` in engine and content source. Scope is deliberate — presentation code may use it for effects that draw no simulation state (particle jitter in `rendering/fxRunner.ts`). Full-line comments are skipped so prose may name the banned call (a line led by `*` counts as one only inside a block comment; elsewhere it continues a multiplication), and a `// purity-allow: <reason>` pragma on or above a line exempts a reasoned entropy-boundary case (today: `ProfileManager`'s profile IDs). A call through an alias (`const M = Math`) is not traced.
   - **Wall clock:** fails on `Date.now()` (or `Date['now']()`) and on `new Date()`/`Date()` with no argument in engine and content source; a `Date` built from a given time reads no clock. Timestamps (save, death, leaderboard, flight-recorder metadata) and the new-run entropy boundary are allowlisted per file, each with a reason, in `scripts/purity-clock-allowlist.json`; a stale entry fails. New floors draw their layout seed from `engine.prng`, and `PRNG`'s default seed is a fixed constant, never the clock.
   - **Engine encapsulation (`npm run check:engine-encapsulation`, `scripts/check-engine-encapsulation.ts`):** complements the import checks by checking *mutation*. It uses the TypeScript type checker, so a write is matched by the declaring class of the member written, not by variable name.
     - In `src/ui/`, `src/rendering/`, `src/main.ts` **and `src/main/**`**, and `src/content/` (tests exempt), it fails on assignment, compound assignment, `++`/`--`, `delete`, or index writes to an engine class member; on writes through a cast of an engine object (`as any`, `as unknown as T`), written inline or through a local alias the cast initialises (`const o = npc as unknown as { greeting: string }; o.greeting = …`, by dot or bracket; R-cotw-19); and on `Object.assign` onto one, or onto such an alias. A pack changes an NPC's lines with `NPC.setDialogue`.
     - In presentation code (which includes `src/main/**`, §3) it also fails on any call into an internal engine subsystem (`GameMap`, `Container`, `InventoryManager`, `StatusManager`, `EnergyScheduler`, and similar) whose name doesn't read as a query (`get`, `is`, `has`, `can`, `find`, `count`, … — deny by default, since a list of mutator verbs missed `consolidateCoins` and `triggerDeath`), dotted or by bracket, on a field written by bracket (`player['hp'] = 0`), on `Reflect.set`/`Object.defineProperty` as on `Object.assign`, and on Array/Map/Set mutator calls against engine members. `GameEngine`, `Player`, and `Entity` methods and `engine.commandBus` are the sanctioned paths.
     - Sanctioned writes (composition-root wiring of `engine.on*` callback slots; content AI strategies publishing `Monster.intent`) are listed with reasons in `scripts/engine-encapsulation-allowlist.json`. A stale allowlist entry also fails the check.
     - It also fails on a write into a plain object or interface-typed value reached through an engine class member (`NESTED_WRITE`, e.g. `engine.lastActionResult.pipelineError = …`), whose own field no class declares, by any mix of dotted and bracket steps (`engine.recentGameEvents[0].turn = …`, `engine.lastActionResult.events[0] = …`).
     - Not traced: writes through a local alias of a member's value (e.g. `const qs = player.quickSpells; qs[0] = x`).
   - **Engine creep (`npm run check:engine-creep`, `scripts/check-engine-creep.ts`):** complements the import checks by checking what engine and presentation code *names*. It loads every pack under `src/content/*/index.ts`, collects the identifiers each pack declares (monster, item, spell, pact, companion, trainer-skill, vault, timed-event, story-trigger, and milestone IDs; choice IDs; town NPC IDs and names; quest references; scripted-vault IDs; and every string under a `…flag` key in choices, timed events, triggers, boss-flee resolutions, and the quest), and fails on any of them appearing in `src/engine/` production source as a quoted literal, a template-literal segment (`` `${n}:blood_tap` ``), an unquoted object key (`{ blood_tap: 3 }`), or, for an ID with an underscore, compounded into a longer string (`'spell~blood_tap'`; a one-word ID inside prose, "cast clairvoyance", is not seen). It also scans presentation source (`src/ui/`, `src/rendering/`, and `src/main/` excluding `src/main.ts`; tests exempt) and fails on any pack-declared identifier in those forms, or a string literal or template segment with a pack namespace prefix (`'<packId>:`, `` `cotw:${id}` ``). Comment lines are skipped.
     - Vocabulary a manifest merely restates from engine enums (equipment slots, elements, status types) is not collected, so it can't collide.
     - Legitimate overlaps — engine built-ins a pack reuses as an ID, engine-owned trigger names, and the engine's built-in starter-kit items — are listed with a reason in `scripts/engine-creep-allowlist.json`. A stale entry fails the check.
     - `scripts/__tests__/engineCreepGate.test.ts` writes a scratch file naming a cotw spell ID to a temp directory, hands it to the gate as engine source (`--engine-file <path>`; `--presentation-file` likewise) and asserts the gate fails; nothing is written under `src/`, where `campaignSeparation.test.ts` walks `src/engine` at the same time. A third case runs the gate on the tree as it is. Against `dc5de31`'s `engine.ts` the gate reports 8 violations (`blood_tap`, `crimson_ward`, `blood_spear`, `siphon_ritual_resolved`).
2. **Determinism & PRNG Discipline:**
   - All simulation randomness — dice, loot drops, spawns, combat rolls, AI choices, hook chance rolls, and generated entity/item IDs — must come from the engine's seeded PRNG.
   - `engine.prng` is the canonical accessor. `engine.rng` is an existing bound delegate (`() => engine.prng.next()`) for APIs that take a `() => number`. Do not introduce further aliases.
   - Simulation code must not use `Math.random()` or wall-clock time (`Date.now()`) to determine outcomes or IDs. Functions that accept an `rng` parameter must receive a seeded source from simulation callers.
   - Every `Math.random` call on a simulation path is gone: rng parameters are required rather than defaulted, and the `engine ? engine.rng() : Math.random()` fallbacks (all unreachable, since those functions take a required `GameEngine`) were removed. `LootEntry.generate` receives the seeded delegate, so content gold drops roll from it.
   - **Entropy boundary:** a run's seed is drawn from the clock exactly once, outside the simulation — `ProfileManager.createCharacter` creates the run PRNG (from `options.seed` when given) and hands it to both the starting-kit roll and the `GameEngine`; `TitleScreen` owns a similar stream for attribute re-rolls before any engine exists.
   - **Not simulation:** `rendering/fxRunner.ts` uses `Math.random` for particle jitter. It draws no simulation state and changes no outcome, so it stays.
   - **Simulation IDs:** `GameEngine.nextSimulationId(prefix)` derives spawned-entity and item IDs from `turnCount` plus a seeded PRNG draw, so one seed replays to the same IDs. Generators that already receive a seeded `rng` (loot, vaults, coin stacks, stack splits) derive their suffixes from it.
   - **Outside the boundary, by design:** save and telemetry timestamps record real time, and `ProfileManager`'s profile IDs stay clock-derived — seeding them would make two characters created from the same seed collide. Those lines carry a `// purity-allow:` pragma (item 1 above).
   - `check:engine-purity` enforces this: it fails on `Math.random`, `crypto` randomness, and an unallowlisted `Date.now()` or `new Date()` in engine and content source (item 1 above).
3. **Schema Evolution Integrity (`npm run validate:schema`, `scripts/validate-schema.ts`):**
   - Passes a current-version save through unmigrated, asserts a save one version below the floor is refused (the v0-v11 chain is gone, ADR-0002, so no v1 envelope can migrate), and runs a probe N -> N+1 step registered by the script, so the next real migration's machinery is exercised.
   - Round-trips a live engine through `serializeGame` -> `JSON.stringify`/`JSON.parse` -> `deserializeGame`, asserting that surface cells (type, duration, potency), ground items, and PRNG state all survive. JSON is in the loop because saves persist as strings, so a value that cannot round-trip through JSON is as lost as one the serializer drops.
   - `PRNG.getState()` returns the raw internal state while `setState()` coerces to int32, so a restored generator reports an equivalent but differently-encoded state. The validator compares int32-normalized states and separately asserts the next draw matches.
   - Per-step migration assertions live in `src/engine/storage/__tests__/migrator.test.ts` (run by `npm test`).
4. **Headless Simulation (`npm run sim`, `scripts/headless-sim.ts`):**
   - **Population anchor:** generates CotW floors through `DungeonArc.generateFloor` across several floors, repeated generations, and the base and pact-boosted monster densities, then derives its data points from the measured counts (realistic median, realistic high, and a labeled stress multiple) instead of a hard-coded population. Placement is seeded per floor (§7.2), so the anchor varies the seed across generations to sample a realistic spread rather than one floor repeatedly.
   - **Scenarios:** a dormant floor (player moves; sleeping monsters outside FOV), an awake floor (hunting monsters path to and attack an invulnerable player), and a 1,000-cast spell workload. After a global JIT warmup, each data point runs a warmup plus repeated samples and reports median and max.
   - **Fails on:** any rejected action, any caught pipeline exception (including isolated monster-turn failures), or a wall-clock budget exceeded by a median at realistic populations. Wall-clock budgets live here, not in `npm test`. `--inject-error` demonstrates the failure path.
   - The long-running chaos/monkey simulation (random actions, save/reload cycles, invariant, deadlock, and NaN assertions) is `src/engine/__tests__/chaosSimulation.test.ts`, run by `npm test`.
   - **Invariant, NaN, and deadlock assertions:** at 100-turn checkpoints and once at scenario end, the sim asserts that player and entity scalars (hp, mana, position, energy, speed, carried weight, `turnCount`) are finite, that speeds are positive, that entities stay in bounds with unique ids, and that a living player has positive HP. A deadlock watch runs every turn: a successful player action that does not advance `turnCount` six times running is reported as a deadlock. Checkpoint scans are timed and subtracted from the scenario's elapsed time, so they never inflate the wall-clock budgets above.
   - Run lengths and results are whatever the latest output reports; this document intentionally does not restate them.
5. **Static Analysis & Build Verification (`npm test`, `npm run lint`, `npm run build`):**
   - `npm test`: runs all Vitest suites (`src/**/__tests__/` and `tests/`). Suite and test counts are whatever the run reports; this document intentionally does not restate them.
   - Test files are not isolated (`isolate: false` in vite.config.ts): a worker runs its files in one module graph, so a file starts from whatever process state the files before it left. A file puts back what it changes: registries, module-level lists such as `AttributeCalculator`'s modifiers, a shared object such as the default manifest of an engine built without one (edit the engine's own copy), stubbed globals (`vi.stubGlobal`, then `vi.unstubAllGlobals()`), and timers that would fire after it ends. `npx vitest run --isolate` runs each file in a fresh graph, to tell a leak from a real failure.
   - The setup file, `tests/setup/sharedState.ts`, runs before each test file. It points the registry facades back at the process defaults, since a `new GameEngine` leaves its own registries active, and it fails a file that leaves a monster, spell, companion or trap in those defaults: no engine module registers one at import, so every engine built after it would be seeded with it. A file that registers such fixtures removes them in `afterAll`: `activateRegistries(null)`, then the facade's `clear()`. `useTestSpells` and `useTestCompanion` (`src/engine/__fixtures__/testHelpers.ts`) register and remove a suite's spells or test companion.
   - Governance references are tested there too: `scripts/__tests__/docReferences.test.ts` fails on a cited `§N` that ARCHITECTURE.md lacks, a cited `P-NN` that is neither registered in §9 nor below its "Next free ID", a `[Planned: P-NN]` tag without a §9 entry, and a relative doc link to a missing file.
   - `npm run lint`: `tsc --noEmit` over the `tsconfig.json` `include` set (`src`, `tests`, `scripts`, `relay/src`, `vite.config.ts`), then `tsc --noEmit -p e2e/tsconfig.json` over the Playwright specs and helpers, `e2e/soak/` included, and `playwright.config.ts` (Playwright strips their types without checking them; the config takes `src/main.ts` along for its `Window` debug handles, so a spec is checked against the engine's real types), then `npm run check:engine-purity`, `npm run check:engine-encapsulation`, `npm run check:engine-creep`, `npm run check:ui-palette` (the color-literal ratchet over presentation source, baseline `scripts/ui-palette-baseline.json`; lower it with `npm run check:ui-palette -- --update` after removing literals; it counts the forms ARCHITECTURE.md §7.2 lists, in stylesheets and in strings alike, but not named colors, and it compares a net count per file, so adding one literal while removing another in the same file passes), and `npm run knip` (`knip.json`: unused files, exports, types, and dependencies all fail the gate). Its entries are `src/main.ts` (which knip's Vite plugin finds through `index.html`), the scripts, the relay worker and the tests, so an engine or pack export counts as used only when one of them reaches it, and dead engine API fails the gate. Tests count as users there; `npx knip --production` leaves them out and lists the exports only tests use, which should be deliberate test seams (reset helpers, fixtures, save round-trip helpers). `knip.json` has no `ignoreIssues` exemptions today; one would exempt a file only while its dead exports wait on another change. knip 6 has no class-member analysis, so an unused method goes unreported.
   - `npm run build`: `tsc && vite build`, verifying single-file production compilation (cotw theme) without type errors or bundler warnings.
