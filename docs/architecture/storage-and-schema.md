# State Normalization, Storage & Schema Evolution

> How saves are shaped, stored, migrated and loaded, and why; [`ARCHITECTURE.md`](../../ARCHITECTURE.md) §5 holds the rules and wins any disagreement (flag it, §8.2).

## State Representation
- **Entities:** `GameMap` keeps a `Map<string, Entity>` keyed by ID, plus spatial indexes (§6). Relationships are scalar IDs (§5's reference invariant).
- **Tiles:** a dense `TileDefinition[][]` grid indexed `[y][x]`; dense arrays are the intended representation for per-cell map data.
- **Ground items:** `Map<string, Item[]>` keyed by plane-qualified coordinate (`planeId:x,y`).
- **Items in containers:** containers hold `Item[]`; each item carries scalar `parentId`/`ownerId`, resolved at runtime through the container registry (`src/engine/items/containerRegistry.ts`). Saves serialize containers as nested item trees carrying those IDs.
- **Flat item index (`src/engine/items/itemIndex.ts`):** lookup by ID goes through a flat `Map<id, { item, location }>` (in a container, on the ground, or in an equipment slot) rather than walking packs, belts, purses, paperdolls and tiles. Entries are written at the choke points every item passes through: `Container.addItem`/`removeItem`, `GameMap.addItemAt`/`removeItemAt`, `Paperdoll.equip`/`unequip`. `removeItemAt` retracts only the ground entry it wrote, so a pickup (stored before the tile is cleared) keeps the newer entry; a stack merged into another retires its id. Deserialization goes through `Container.placeItem`, which registers like `addItem` but skips capacity checks and merging, so a load rebuilds the index with no schema change. `EngineCommandBus.resolveItem` resolves through it; scoped questions ("in *this* inventory?") stay structural (`InventoryManager.findItemById`). This is a second structure tracking a first, which is how the scheduler partition failed ([ADR-0001](../decisions/0001-scheduler-partitioning-evaluated-not-adopted.md)), so `itemIndex.test.ts` audits it against a full structural scan after a save/load round trip.

## What a Save Holds
A save holds what a run can change, and nothing a definition already says.
- **Additive fields need no schema bump.** A new field is optional, written only when it differs from its default, and a save without it loads as the default, which is what that save always meant. Most of `SerializedPlayer`, `SerializedMonster`, `SerializedItem`, `SerializedContainer`, `SerializedMap` and `SaveData` grew this way; only a change an old save can't be read under bumps the version (§5).
- **Definition data comes back from the manifest.** An item's or container's definition-only fields (potion `effects`, `twoHanded`, `rangedConfig`, `predicate`, `hooks`, `wornEffects`, capacity) are restored from the definition named by `definitionId`, as `createScaledItem` gives them to a new item and as monsters get their loot tables, tags and hooks back. A definition change therefore reaches items already found, while what was rolled onto an item stays put: family modifiers are saved whole (`SerializedItemModifier`), so a template change never alters an item in hand. Perks are saved by id and resolved against the pack on load.
- **Loads rebuild, never replay rules.** The paperdoll is put back slot by slot as worn (`Paperdoll.restore`), not through the equip rules, which run before the hero (and the perks that bend them) exist; containers reload their children without merging, so split stacks stay split. A saved shape the game has since outgrown is settled after the restore (`InventoryManager.settlePurse` moves coins a purse no longer has room for to the pack).
- **Derived state is not saved.** Category kill totals come from per-species kills; a floor's light (`GameMap.lit`) and a prologue's state are re-derived on load.
- **Merchant stock** is `SaveData.merchantStock`. `MerchantConfig.initialInventory` is a factory called once per town built and once per load, so no hero's purchases reach another's shop.

## Seeded PRNG Serialization
`PRNG` (`src/engine/dungeon/prng.ts`, Mulberry32) keeps one 32-bit state, saved as `SaveData.prngState` via `getState()` and restored with `setState()`, so the stream resumes exactly where it stopped. Randomness and spawned-entity IDs both come from it (§7.2); save timestamps and profile IDs are deliberately outside that boundary.

## Persistence
- **`localStorage`:** the synchronous default for character saves (`ProfileManager`) and autosaves (`AutosaveManager`, periodic and on floor change). Both live in `src/engine/storage/` and take a `Storage`-shaped adapter; the browser's comes from `getBrowserStorage()` (`src/ui/platform.ts`), and `src/ui/persistenceInit.ts` asks for persistent storage at boot.
- **Per-pack keys:** every engine-owned key derives from the active manifest id (`ProfileManager.rosterKey`/`saveKeyPrefix`, `AutosaveManager.autosaveKey`), so two packs on one origin never touch each other's saves. There is no un-namespaced fallback: a bare key left by anything else is ignored, never adopted.
- **Quota:** map tiles and explored cells are run-length encoded (`compaction.ts`). Tile runs use a per-map dictionary (`tileCodes` on `SerializedMap`, `${count}:${index};` tokens), the only tile codec, so arbitrary content tiles fit; run-length data arriving without a dictionary is recorded by the flight recorder, never decoded into walls. Saves stay whole: every save, autosave and replay checkpoint carries every visited floor inline.
- **Asynchronous tier (`src/engine/storage/asyncStore.ts`):** `AsyncKeyValueStore` is the contract for records kept outside the synchronous quota (bestiary records, flight-recorder logs). The engine defines only the interface, since `indexedDB` is a browser global (§2): `IndexedDbStore` lives in `src/ui/indexedDbStore.ts` and the composition root injects it; `InMemoryAsyncStore` backs tests and `npm run sim`. `BulkArchive` (`bulkArchive.ts`) is the typed surface over it, keyed per profile; an archive failure is swallowed so it can never mask the crash it is recording.
- **Export and import:** a `.cotw` file download (`src/ui/platform.ts`), file and drag-and-drop import (`src/ui/saveImporter.ts`) and Base64 save codes (`src/engine/storage/saveTransfer.ts`) give offline backup and transfer. A save code names its hero `shared-hero` in place of the profile id; import replaces an id the roster already has with a fresh one.

## Forward-Only Schema Migrations
Saves are wrapped in a `VersionedSaveEnvelope` (`schemaVersion`, `contentManifestId`, `timestamp`, `data`). `CURRENT_SCHEMA_VERSION` in `migrator.ts` is authoritative; don't restate its value elsewhere. `SchemaMigrator.migrate()` applies registered `N -> N+1` steps in sequence and throws when the payload is unparseable, newer than the engine, missing a step, or a step fails. A save below the floor is refused (`migration-failed`); the old v0 -> v11 chain was deleted pre-launch ([ADR-0002](../decisions/0002-v0-v11-migration-chain-deletion.md)), but the registration and sequencing machinery stays, exercised by `npm run validate:schema` and `migrator.test.ts`, so the next real migration behaves as before.

## Load Failure Handling
- **The live game's registries are left alone:** a load builds its map and items before their engine exists, so `deserializeGame` builds them under a fresh item index and container store, and if it throws it reactivates the bundle that was active (`activeRegistries`/`activateRegistries`). A damaged save can't leave the live game's item ids resolving to discarded copies.
- **Sizes in a save are checked, not trusted:** a map whose width or height isn't a whole number from 1 to 512, tile runs covering more cells than the map has, or more than 256 stored floors is refused as `corrupt` before anything is allocated for it, and FOV runs are read only to the map's last cell, so a crafted `.cotw` can't freeze the tab.
- **Typed outcomes:** `ProfileManager.loadCharacterResult()` and `AutosaveManager.loadAutosaveResult()` return a `LoadOutcome` (`loadResult.ts`): the game, or a failure naming `missing`, `corrupt`, `newer-than-engine` or `migration-failed`, with a player-facing message and the error as `detail`. `classifyLoadError` maps `SchemaMigrator`'s messages; anything unrecognized is `corrupt`. `src/main.ts` toasts every failure but `missing`, which is routine (a fresh start, no autosave yet).

## Death and Continue
`ProfileManager.saveCharacter` and `AutosaveManager.autosave` skip the payload write when the hero is dead; the death still updates the roster (`questStatus`, epitaph, level), so the Hall of Fame records it while the slot keeps the last living save. `resolveContinueTarget` (`continueTarget.ts`) is the one rule behind Continue: the autosave if its hero hasn't fallen, else the most recently saved living hero, else nothing. A fallen hero's earlier saves stay loadable from Load Saved Game, as a living run.

## Autosave Preservation
The autosave key is per pack, not per hero, so any later autosave (another hero's, or the same hero's after climbing back or loading an older save) would replace it. `AutosaveManager.autosave` therefore calls `preserveIfSuperseded` first: the current autosave is copied verbatim to `<manifest>_autosave_preserved` when it belongs to another hero or is deeper than the incoming one, unless the preserved slot already holds the same hero's deeper run. A failed preserve write is recorded and never blocks the autosave. `AutosaveSlot` (`'latest' | 'preserved'`) selects the slot; Load Saved Game shows the preserved one as "Earlier Autosave", while Continue uses only the latest. Cost: one extra full save in `localStorage`, only after a superseding autosave.
