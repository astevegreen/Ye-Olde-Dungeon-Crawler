# Progression & Scaling

> Topic doc under [content-extensibility.md](content-extensibility.md) ([ARCHITECTURE.md](../../ARCHITECTURE.md) §3). Explanatory only — every binding rule about content integration lives on the guaranteed-read path (`ARCHITECTURE.md`'s §3 stub and `content-extensibility.md`'s core sections), never only here. Flag a conflict rather than resolving it here (§8.2).

## Milestone Renown Ledger
`manifest.renownMilestones` (`RenownMilestoneDefinition[]`) declares per-category, cumulative renown milestones (one-time or repeatable); `manifest.renownTitles` declares title thresholds per category or across the total. `src/engine/renown/renownLedger.ts`'s `recordMilestone(engine, id)` is called at generic engine trigger points (`UncurseAction` on cleansing a curse, `SearchAction` on finding a secret door) — a no-op if no milestone with that ID is defined, the same "engine calls a generic hook, content may or may not react" pattern as `emitDiscovery`. Renown is per-character: it rides entirely on the existing `WorldState.counters`/`flags` (`renown:<category>` counters, `renown_milestone_earned:<id>` flags), which already serialize with the save — no `SaveData` field or migration step was needed. Vendor unlocks need no new predicate type either: `Predicate`'s existing `minCounter` variant, evaluated against a `renown:<category>` counter, already gates a `MerchantConfig`/`Item.predicate`-filtered stock item (see `Merchant.getAvailableStock`, now actually consulted by `ShopOverlay.getBuyableItems` — previously present but unused by the live UI). The active title is surfaced in the character header (`getActiveTitle(engine)`).

## Tag-Filtered Radial Auras
`MonsterDefinition.tags?: string[]` (wired through `createScaledMonster`/`Monster.createFromDefinition`) sets tags resolved at runtime via the pre-existing `Entity.tags`/`hasTag()` (which already also matches faction and entity type). `findTaggedEntitiesInRadius` (`src/engine/combat/radialAuraFilter.ts`) is the generic, reusable piece: a bounded-radius (§6-style, no unbounded scans), any-of-`tags` entity query, shared by two call sites — `HookDispatcher`'s `radialAuraFilter` `ActionPrimitive` (applies a nested primitive to every match; item/monster hooks) and `DrinkPotionAction`'s `radial_status` consumable effect (applies a status to every match; potions/deployables). Tag matching is a flat any-of-`tags` list, not a boolean `and`/`or`/`not` expression tree — simpler than originally designed and consistent with how `hasTag()` is already used elsewhere (e.g. `combat.ts`'s damage-affinity bonuses).

## Level-Scaled Elemental Resistance
`resolveLevelScaledResistance(curve, level)`/`applyLevelScaledElementalMitigation(amount, level, curve)` (`stats/levelScaledResistance.ts`) resolve a numeric mitigation fraction from an ascending `{level, resistance}` step curve — the first real consumer of `calculateAttribute`'s long-reserved but previously-unused `'elementalResistance'` attribute key. Declared per-element on `ProgressionConfig.elementalResistanceCurve`. Deliberately *not* wired into `Entity.takeElementalDamage`/the categorical `elementalResistances` affinity system combat already uses (untouched, so this can't regress it). Its original consumer was removed and replaced by a different mechanic — see [ADR-0003](../decisions/0003-jarnvidr-exposure-handler-to-giant-blood.md). The module remains as unused-but-legitimate generic engine capability; no other content pack consumes it today.

## Zone-Tiered, Difficulty-Scaled Monster Power
`types/monsterScaling.ts`, `dungeon/spawner.ts` (2026-09-18): replaces `cotw`'s old flat per-floor scaling curve with a step function over content-declared `MonsterPowerTier[]` breakpoints (`{floor, multiplier}`, ascending, same step-curve idiom as Level-Scaled Elemental Resistance above), combined with a difficulty's two knobs — `basePowerMultiplier` (a uniform shift, including at the first tier) and `scalingRateMultiplier` (scales only the tier curve's growth *above* 1.0) — plus an optional `bossPowerFloorMultiplier` that floors a `boss`/`miniboss`-tagged `MonsterDefinition`'s multiplier at `tier * bossPowerFloorMultiplier`, so a low-difficulty base power can't trivialize a guarded fight. `GameContentManifest.monsterScaling?: MonsterScalingConfig` is optional; `scaleMonsterStats`/`createScaledMonster`/`populateDungeonFloor` fall back to the original flat curve byte-for-byte when it's omitted (e.g. `warcraft`, which doesn't set it), so this is purely additive. `cotw`'s own `COTW_MONSTER_SCALING` (`content/cotw/monsterScaling.ts`) ties its seven tiers to the real zone `minFloor` bands (Rime Hollows, Abandoned Dwarven Works, Obsidian Siphon, Tarnished Silver Veins, World Bark Descent, Maw of Malice, the floor-50 climax) and climbs continuously across the Act 1 → Act 2 boundary — no reset, since Act 2 is pure escalating monster power with no thematic tie-in of its own. Threading `difficulty` (a `Player`/save concept) down to where floors are actually generated required two additive trailing-argument changes at `engine.ts`'s `changeFloor()` (the real per-floor generation call) and its `diagnostics.spawnMonster` triage tool — both minimal, no new logic added to `engine.ts` itself (§8.1 exception: none of the three literally applied, authorized as an explicit, narrowly-scoped exception for this change).

## Permanent Stat Modification & Companion Grants
`ChoiceConsequence` (`types/choice.ts`) gained `modifyPermanentStat` (adjusts `Player.attack`/`defense`'s *raw base* — via `baseAttackValue`/`baseDefenseValue`, not the equipment-inclusive getter, which would double-count gear bonuses on every future equip/unequip — so a story choice can permanently reshape a build) and `grantCompanion` (bonds the acquisition-gate flag and calls `summonCompanion`, so a story beat can grant a pet without a trainer visit). The consequence-interpreter loop was factored out of `ExecuteChoiceAction` into an exported `applyConsequences(consequences, engine, player)` so other triggers — see [content-quests-and-triggers.md](content-quests-and-triggers.md) — reuse the exact same, tested semantics instead of a second interpreter.
