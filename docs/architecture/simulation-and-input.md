# Simulation Scoping & Input Architecture

> Sub-document of [`ARCHITECTURE.md`](../../ARCHITECTURE.md) §6 stub. This file is **explanatory**: mechanism detail and worked examples. Every **binding** rule — bounded simulation scoping, the modal-stack focus rule — is restated in the core document's §6 stub. If this file and the core document ever disagree, the core document wins; flag the conflict rather than resolving it here (`ARCHITECTURE.md` §8.2).

- **Bounded Simulation Scoping:** Simulating multiple floors at once is prohibited. Visited floors other than the active one are stored (`engine.storedFloors`) and not simulated. Within the active floor, per-actor work is throttled:
  - **Dormant Actor Scheduling:** Every living actor on the active floor stays in `EnergyScheduler` and accrues energy. On a monster's turn, `Monster.takeTurn()` does the following, in order:
    1. Resolves status-effect ticks (`statusManager.tick()`), always, sleeping or not.
    2. Checks paralysis/stun.
    3. Calls `MonsterAI.decideAction()`. Inside it, any pending wind-up and the spell-cooldown decrement resolve first. A monster with `aiState === 'sleeping'` then wakes if it has line of sight to the player within Euclidean distance 8 or stands on a tile visible in the player's FOV. Otherwise it returns a `WaitAction` without pathfinding, item use, or combat resolution.
    - `GameEngine.updateFov()` also wakes sleeping monsters on visible tiles.
    - Companions (§3) never sleep (`aiState: 'hunting'` always) and are registered on `EnergyScheduler` like any other active-floor actor — no new scoping exception to this bounded-simulation model.
  - **Scheduler Partitioning (Evaluated, Not Adopted):** an active/dormant scheduler partition was implemented, benchmarked, and reverted. See [ADR-0001](../decisions/0001-scheduler-partitioning-evaluated-not-adopted.md) for the full evidence and rationale. `EnergyScheduler` uses a single flat entity list today. Review that ADR before re-attempting the same partition.
  - **Bounded FOV Awakenings:** `FovManager` computes visibility with recursive shadowcasting limited to the player's radius (default 8, adjusted by pact modifiers). Monster awakenings and bestiary records are checked only across the bounding box `[minX..maxX, minY..maxY]` of the player's vision. Each update demotes only the tiles the previous pass lit: `FovManager` tracks them as packed indices, so the cost follows the view, not the map. Anything marked visible outside the shadowcasting pass (`setVisibility`) is tracked the same way, and `revealAll` sets a flag that makes the next update fall back to one full sweep — tracking every index there would cost more than the sweep it saves. `lastDemotedTiles` exposes the count for diagnostics.
  - **Perception-Radius Override:** any active status whose handler declares `StatusHandler.perceptionRadius` forces `updateFov()`'s radius to that value (the most restrictive wins if several are active) — a generic mechanism, not a hardcoded per-status check. `blindness` and `sensory_masked` both declare `perceptionRadius: 1` today.
  - **Sensory Masking & Echolocation:** the `sensory_masked` status (content-applied, e.g. a Bat Senses Potion) cripples FOV to radius 1 via the override above, and separately lets the renderer detect things beyond it: `getAudibleEntitiesInRadius`/`getAudibleTilesInRadius` (`src/engine/fov/echolocation.ts`, radius `ECHOLOCATION_HEARING_RADIUS` = 6) find non-dormant actors (a sleeping monster makes no noise) and noisy terrain (inherently audible tile types, or an active surface/gas/trap) within a bounded query. `CanvasRenderer.renderEcholocationView()` (`src/rendering/canvas-renderer.ts`) replaces the normal tile/entity pass while the status is active: a blank board, the player's own icon, and only audible actors (reusing the existing ESP-detected pulsing-indicator style) and terrain. The underlying FOV/awakening simulation is unchanged — only what gets drawn changes.
  - **Spatial Bucketing:** Entity lookups use constant-time coordinate bucket maps (`entityBuckets: Map<string, Entity[]>` keyed `"x,y"` in `GameMap`), so proximity and collision checks do not scale with total monster count.
  - **Modal Pause:** Pushing the first modal onto `ModalStackManager` sets `engine.isPaused`, and `advanceWorldUntilPlayerTurn()` does nothing while paused.
- **Input Architecture:** `InputHandler` (`src/rendering/input-handler.ts`) owns the `window` `keydown`/`keyup`/`blur` listeners, the `ModalStackManager`, and the `ChordBuffer`.
- **`ChordBuffer` Mechanics (`src/ui/input/chordBuffer.ts`):**
  - **Sliding-Window Arrow Chording:** When `arrowChordingEnabled` is on (the default), orthogonal arrow keypresses within the micro-debounce window (`arrowChordBufferMs`, default 40ms, clamped to 25–75ms) combine into a diagonal (e.g., Up + Right -> NorthEast). When it is off, arrows move cardinally with no buffering.
  - **Keyup Flush:** Releasing an arrow key before the debounce timer expires dispatches the pending cardinal step immediately — `handleKeyUp` calls `flush()` when the released key is the one that started the pending step, since no chord can follow it. Waiting out the window after the key is already up is latency the player feels on every step. A chord that formed before release still wins, and the release emits nothing further.
  - **Key-Repeat Bypass:** While an arrow key or an active diagonal chord is held and the browser sends repeat events (`KeyboardEvent.repeat`), the buffer skips the debounce timer and dispatches a move on each repeat.
  - **Opposing Direction Reversal:** Pressing the opposite key while a step is pending (e.g. Left while Right is pending) cancels the pending move and immediately honors the new direction.
  - **Focus Loss:** Window `blur` clears all held-key state.
  - **Multi-Scheme Directional Controls:** Default bindings live in `src/ui/settings/settingsManager.ts`. Only arrow keys go through `ChordBuffer`; the other schemes dispatch immediately:
    1. Arrow keys (chorded or instant cardinal mode).
    2. Roguelike Numpad 1–9: diagonals 7, 9, 1, 3; cardinals 8, 2, 4, 6; center 5 to wait.
    3. Vi keys: H, J, K, Y, N by default. L, U, and B open Look, attribute allocation, and the Bestiary, so vi users rebind those directions in Settings.
    4. WASD: W, A, D by default; S is Search.
    - Every default key maps to exactly one action; `src/ui/__tests__/defaultKeybinds.test.ts` enforces it, including the keys `InputHandler` hard-wires (U, E).
- **Configurable Radial Action Menu (`src/rendering/radialMenu.ts`):** a hold-to-open canvas overlay bound to the configurable `radial_menu` action (default `KeyV`, remappable through the same `SettingsManager`/`ACTION_METADATA` keybind system as every other action). While held, the same directional-key vocabulary above (arrows/WASD/vi/numpad) selects one of 8 compass wedges instead of moving; releasing the trigger key confirms the hovered wedge, `Escape` cancels. Slots (`SettingsManager.radialMenuSlots`, keyed by the fixed 8-direction order) are `{ type: 'spell' }`, `{ type: 'command' }` (dispatched via `CommandPalette.getCommand`), or `{ type: 'item' }` (a potion or self-targeted scroll resolved via `InventoryManager.findItemById` — aimed items that need a target reticle, like wands, are not a fit for direct radial activation). It registers on `ModalStackManager` like other overlays. Gamepad invocation is not implemented and is deliberately out of scope. **[Deferred: P-24]**
- **Potion row (`src/ui/potionRow.ts`):** four slots beside the health orb, each pinned to a potion kind (`Player.quickPotions`, saved with the character; keyed by `potionKindKey`: definition ID, else the true name, never shown). The first time a hero has no pins, the kinds they carry are pinned in order; after that only the player changes pins, by right-clicking a slot or clicking an empty one (a picker that registers on `ModalStackManager`). A slot whose kind has run out stays, dimmed, with a zero count. A click or the `drink_potion_1..4` actions (default `Shift+Digit1..4`) drink via `handlePlayerAction(DrinkPotionAction)`, the radial menu's path; a key on an empty slot opens its picker. `InputHandler` checks these bindings before its bare-digit quick-spell keys, which would otherwise read `Shift+1` as spell slot 1.
- **Command palette (`src/ui/help/commandPalette.ts`):** a `UIModal` that pushes itself onto `ModalStackManager` when it opens and removes itself when it closes. `Ctrl+K`/`Cmd+K` or `Shift+/` toggles it (`InputHandler.onToggleCommandPalette`), only when no other modal is on top.
- **Focus & Modal Isolation:**
  - **Rule:** every open modal registers on the LIFO `ModalStackManager` (`src/ui/modalStack.ts`).
  - **Stack behavior:** the top modal receives all keystrokes. If it does not handle `Escape`, the stack pops it. All other keys are trapped so they never reach the simulation. Modal handlers call `event.preventDefault()` for keys they consume, which prevents browser shortcut conflicts.
  - **Registered:** every in-game modal. Character menu (`CharacterMenuModal`, `id = 'character-menu'`, the only home of the spellbook, bestiary, pacts, attribute allocation and the Rune of Return ranks), inventory, targeting, diagnostics, context help, the radial menu, the shop overlay, choice, mastery-perk choice, save & quit, settings/keybinds, save-code, feedback, and the Rune of Return discovery modal. The feedback modal (`src/ui/feedbackModal.ts`) and the settings/keybind modal (`src/ui/settings/keybindModal.ts`) also open from the main menu, where `InputHandler` is disabled, so each takes keys through a `keydown` listener on its own focus-holding overlay element — never a second `window` listener — and stops their propagation, so each key reaches its `handleKeyDown` once; each pushes and removes its own single stack entry. That listener runs before `InputHandler`'s, which is what rebinding needs: the settings modal refocuses its overlay after re-rendering its keybind list, so the key to bind reaches it before `InputHandler` would claim F1/F2/F3 or the backquote. (Dwarven Winch and town-return modals were removed 2026-09-16 along with their underlying mechanics.)
  - **No accidental commits:** windows that open mid-move (choice, mastery-perk choice, and the Character tab a level-up opens) swallow keys for 200 ms after opening (`CharacterTab.guardInput`) and only stage a selection until Enter or a confirm button locks it in; attributes never take number keys. A level's points — attributes and Rune of Return ranks alike — are planned in `AttributeAllocationDraft` (`src/ui/attributeAllocationDraft.ts`) and reach the player only on Accept, through `Player.allocateAttribute` and `allocateRuneMastery`; Escape closes the menu without spending, and points locked in earlier can never be taken back.
  - **`UIModal` Normalization & Consolidated Character Menu:** Modals implement the `UIModal` interface (`id`, `isOpen`, `handleKeyDown(e): boolean`, `close()`). `CharacterMenuModal` (`src/ui/characterMenu/characterMenuModal.ts`, styled by `src/ui/styles/menu.css`) consolidates primary player screens into one tabbed shell that owns all the chrome (ADR-0011): the tab strip (key chip, label, a badge such as unspent points), the one close button, and a footer of the active tab's keys and actions, which a tab supplies through `MenuTab.footer()`; tabs draw only their content and decline the keys they don't use. Tabs fill the window less a 20px margin, except the canvas-drawn inventory (`drawsOnCanvas`), where the shell shrinks to the window the inventory draws and lays its tab strip over that window's title bar:
    1. **Inventory:** Canvas-based overlay adapted via `InventoryTabAdapter` (`src/rendering/inventoryTabAdapter.ts`).
    2. **Character:** identity and vitals, the only allocation UI (S/D/C/I plan a point, Shift+letter removes one, −/+ buttons, previews from the engine's formulas, an "If you accept" before→after list) with attribute milestones, and the Rune of Return ranks (1/2/3), which spend the same points (`src/ui/characterMenu/characterTab.ts`). Leveling up, U, the `allocate-stats` command and the header's points button open it; every "rune tree" entry point (Shift+T, the discovery dialog, the inventory, the rune-smith) opens it at the ranks.
    3. **Spellbook:** Spell selection and casting mode (`SpellbookTabAdapter`).
    4. **Bestiary:** Defeated monster compendium (`CompendiumTabAdapter`).
    5. **Pacts:** Ancient run pacts and bounties (`PactTabAdapter`).
    6. **Story:** `StoryTab` (`src/ui/characterMenu/storyTab.ts`, model in `storyModel.ts`): the Descent line, the Saga (objective, deeds done, locked deeds as riddles, the Chronicle of discovery events), and lore, standing and sealed pacts (Left/Right). See content-quests-and-triggers.md, Story Presentation.
    - **Dependency Inversion & Engine Purity:** The shell consumes tabs through the `MenuTab` interface (`src/ui/characterMenu/menuTab.ts`). `src/ui/` only imports types from `src/rendering/`; `InventoryTabAdapter` lives in `src/rendering/` to satisfy engine-purity quality gates.
    - **Hotkeys & Navigation:** Tabs cycle via `Tab` / `Shift+Tab`; a tab that claims Tab (the inventory's panels) keeps it until it reaches its edge, and Shift+Tab enters such a tab on its last panel. Each tab's action keys (`inventory` I, `character_menu` E, `cast_spell` Z, `compendium` B, `pact` P, `story` O by default) open it from the game via `InputHandler.toggleCharacterMenu(tabId)`, and switch to it inside the menu once the active tab declines the key; the shell reads them from the player's keybindings (`setKeyResolver`), so chips and keys follow rebinding. The active tab's own key closes the menu.
  - **Still intercepted inline by `InputHandler`:** the map and inspect overlays. Right after modal-stack routing, an open map receives every key (`MapOverlay.handleKeyDown` closes on M/Esc/Space, pages floors, and absorbs the rest), so nothing reaches the simulation beneath it; the inspect overlay is checked the same way before other keys dispatch. This is equivalent to stack gating for a single non-nesting overlay, and `mapOverlayInput.test.ts` covers it.
  - **Screen-level, not modals:** `InputHandler.enabled` remains for whole-screen transitions — entering the game, returning to the main menu, the game-over screen, and the title/saga screens. Those are not modals over a live simulation, so the stack does not apply.
- **HUD Bars & Viewport Scaling:** the viewport/letterboxing behavior comes from a 2026-09-16 overhaul ([ADR-0004](../decisions/0004-hud-overhaul-retrospective.md)); the HUD layout itself has since changed. Current state: `ViewportManager.recalculate()` (`src/rendering/viewport.ts`) subtracts the real mounted height of every HUD bar (a bar nested in another listed bar counts once) and the width of side columns (`SIDE_COLUMN_IDS`: the combat sidebar), and re-runs on a `ResizeObserver`. Above the map sits the hero square (name, depth, level with an experience bar, renown; a pulsing badge when attribute points are unspent) beside two bars: screens and system (Bestiary, Cmds, Help, Feedback, Dev, `☰ [Esc] Menu`) over actions (Inv, Cast, Look, Map, Rest, Wait, Search, Stairs). Buttons collapse via `@container` queries instead of wrapping. The canvas reserves no strip: map/look/aim/grimoire controls draw as a pill over the bottom of the map while that mode is open. Below the map: the action console and the message log as its last row. The console holds, left to right, the health orb, the potion row, the context action button (`src/ui/console/`: the one thing worth doing here, in priority order attack an adjacent monster, take loot underfoot, use stairs, talk, open a door, rest when hurt with nothing in sight, close a door; `F` or a click), the spell belt with the pack's current objective under it (`getCurrentObjective`, plus the nearest known stairs down; dropped by a container query when the belt's column is too narrow), a tray of chips shown only while relevant (Rune of Return charges or channeling, overflow debt, sealed pacts) with the companion card beneath, and the mana orb. `ViewportManager` also observes each bar's own size, so a console that grows re-fits the canvas. There is no turn counter on the HUD.
- **Combat sidebar (`src/ui/sidebar/`):** a column beside the map at full HUD height, replacing the old widescreen flank panels (what they showed lives on in the character menu's Story tab; packs no longer declare a `flankLayout`). Sections: a minimap (`CanvasRenderer.drawMinimap`, click for the full map), monsters in sight nearest first with HP and any wind-up, the hero's conditions with turns left (statuses, sensing spells, story countdowns, encumbrance), and ground items in sight with what the hero stands on. `sidebarModel.ts` computes each section without the DOM. Pointing at a monster links both ways: hovering a row calls `CanvasRenderer.pointAtTile` (brackets and card on the map), and the renderer's `onFocusEntityChanged` (mouse hover or look reticle) highlights the row.
